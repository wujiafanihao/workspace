## 1. 动机（为什么做）

用户在「百科类」产品里最核心的入口之一是 **搜索**：输入词 → 看到候选词条列表 → 点进详情。

我们已用 js-reverse 等方法 **观察** 过公开站的搜索交互与 JSON 字段形状（见 docs/03）。接下来要做的不是「继续依赖对方 BFF」，而是：

> 在 **自建词条库（self-built lemma DB / 自建存储）** 上，提供 **体验等价** 的搜索能力。

这样产品可独立运营、可合规演进，观察结果只服务「字段与交互设计」。

---

## 2. 目标（做成什么样）

### 2.1 产品目标

- 用户在自有前端输入关键词，得到与「熟悉的百科搜索」**同构的结果列表体验**（标题、摘要、跳转 id、必要徽标等——以合同字段为准）。
- 数据 **只读自建存储**（CMS/DB/检索索引），不在生产路径上实时请求百度 search。

### 2.2 工程目标（文档阶段）

- 冻结 **P0 HTTP 合同**：异步 FastAPI 风格的 `GET /api/search`（详见 `design.md`），与 docs/03 对齐。
- 明确字段映射表（观察键 → 自建键）。
- 列出后续实现待办；**本阶段以规划 / mock 合同为主，不写业务源码。**

## 3. 范围 / 非范围

### 3.1 范围内（In Scope）

| 项 | 说明 |
|----|------|
| P0 搜索 API 合同 | 方法、路径、查询参数、成功/错误码、list item 字段 |
| 字段映射 | 对照观察 JSON 与 docs/03；并用 MCP 再验 |
| 可选 P1 设计占位 | Redis 缓存、suggest（联想）API——只写设计，不实现 |

| 项 | 说明 |
|----|------|
| FastAPI / 检索引擎实现代码 | 留待后续；todo 里标 pending |

| 词条详情页全文渲染 | 可另开计划 |
| 复杂相关性调参 / 个性化排序 | P0 只需「可搜、字段齐、错误码清」 |
| 前端页面实现 | 见 [../20260919前端页面/](../20260919前端页面/) |

## 4. 验收标准（Acceptance）

### 4.1 P0（必须）

1. **API 合同**与 [`docs/03`](../../../docs/python/baiduWiki/) 中搜索章节一致（路径、参数、list item 关键字段、错误码语义）。
2. `design.md` 中有完整字段映射表，并注明「以 MCP 再验为准」。
3. 明确数据源 = **自建 lemma 存储**；架构图/文字中 **无**「生产默认打百度 BFF」。
4. `todo.md` 中规划/合同/mock 任务可勾选；代码实现任务标为后续 pending。
5. `check.md` 文首 `status: in_progress`，代码项保持未勾选直至实现阶段。

### 4.2 P1（可延后，设计可先占位）

- Redis 缓存键设计、TTL、穿透保护思路。
- `suggest` 联想 API 草图（可与搜索共用索引）。

### 4.3 证据

- MCP 导出的 search 样例路径（本地 exports，勿强行提交密钥/隐私）。
- 与 docs/03 的差异表（若有），写在 design 或 check 备注。

## 5. 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 观察字段与线上不一致 | 前端 mock / 后端合同返工 | 计划内「对照 MCP 再验一次字段」 |
| 误把 token 方案写进架构 | 合规与稳定性风险 | 本 plan / design 明文禁止生产依赖 |
| 自建库召回差 | UX 不等价 | P0 先合同与最小召回；相关性迭代另开 |
| 敏感词策略不同 | 错误码与文案不一致 | 自建错误码表；1001 仅作观察参考 |
| 范围膨胀到详情/编辑 | 计划失控 | 非范围写死；另开文件夹 |
